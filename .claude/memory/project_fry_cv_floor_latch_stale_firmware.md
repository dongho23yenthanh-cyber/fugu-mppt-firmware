fry's mid-morning/absorption power drop-outs (e.g. 2026-06-10 ~09:15: P collapsed 224W→7W, Vin rose to ~77V Voc, duty 840→445, recovered after the periodic re-sweep) are NOT a converter/ADC fault and NOT pack termination (`term 0`, highest cell ~3.39V vs vcTerm 3.50V). Root cause: **fry runs firmware that predates the CV-floor-latch fix.**

Mechanism: on the SHARED caravan battery bus, fry & flat both regulate Vout. fry's CV target (`charger.Vout_max() = min(Vbat_max, vpack_pin)`) was stuck at **26.800V = Vbat_fallback (8×cv_min 3.35)** while flat held **27.819V**. Old code (fry) ratchets `vpack_pin` down via EOC feedback when it briefly has bus authority, then once flat takes the bus fry loses authority and the old code has **no path to release the pin back up** → latched at the float/floor voltage, below the bus flat maintains → fry stays floored, yields all charging to flat. flat (newer fw) releases the pin upward when it loses authority, so it never latches → flat had ZERO power dips, fry had several.

Fix already in `main`: commit **32540e31** "charger: gate EOC vpack_pin feedback on Vout authority (fix shared-pack CV-floor latch)" (2026-06-09 12:14). Adds `releaseVoutPinning()` + `voutAuthority` gate in `charger.h::_updatePackVoltagePinning`. **NOT in fry** (was running `c5e8b8b2` fry-brk1-103, commit dated 2026-06-09 10:20, built 15:39 — predates the 12:14 fix), **IS in flat** (`2a9308fc` fry-brk1-102).

**RESOLVED 2026-06-10:** OTA'd fry up to current main `c2a53208` fry-brk1-112 (has the fix). Confirmation it took: lag dropped from latched **68ms → 2.7ms** (newer MCPWM-latency build; flat on -102 still shows 79ms), and fry now holds Vout ~27.27V at 325W competing on the shared bus instead of being squeezed to 26.8V. OTA was bumpy: ota.py's telnet monitor dropped at 1% (fry's flaky NAT link) but fry kept downloading from the :9000 HTTP server independently and completed; ~3min cold-start "no MPP (best 0.00W), backoff" dance after reboot before it swept and converged — that dance is normal fry cold-start, not a fault. STILL TO CONFIRM: no drop-out during the next absorption phase (cells → EOC).

Gotcha that delayed diagnosis: fry & flat were on **different firmware versions**, AND `elf_archive.py list` was STALE for fry (last archived flash June 7 -91, but fry was actually running -103 from a later untracked flash). Get fry's true version live (ota.py version table / boot banner), not from the archive. Also fry's 09:11–09:19 MQTT/console blackout meant its own mppt/charger reason-logs for the 09:15 dip never reached havan's `pv/fugu_console.log`; recovered the power trace from the independent InfluxDB UDP path ([[reference_mppt_telemetry_influx]], console=UTC+1 vs influx UTC). Separately, both devices' MQTT log link flaps all day (overlapping gaps, no WiFi re-assoc) = shared NAT/broker path, benign to charging.

**Follow-on bug + fix (2026-06-10): short power drops on BOTH fry & flat = releaseVoutPinning released DOWN to Vbat_fallback.** Symptom: every ~30-min periodic sweep (or any authority loss / BMS-stale glide) dropped the Vout pin to Vbat_fallback (flat ≈27.04V = 8×3.38), which on the shared bus equals the resting pack voltage → converter immediately CV-limited there → throttled to ~90W for minutes (flat 11:59 dropped 590W→90W for ~3min) even though battery NOT full (term 0, cells ~3.45V IR-inflated under 37A). Vout target = min(Vbat_max=29, vpack_pin); vpack_pin released to fallback was the binding limit, NOT vout_max. voutAuthority (main.cpp:751) = !disabled && duty>min && iout>0.5A — false right after a sweep. Fix: **commit 0bb5fb2** makes `releaseVoutPinning` (charger.h:374) target Vbat_max not Vbat_fallback (cells still monitored on that path → EOC feedback re-clamps; matches bulk target, no setpoint jump). Deployed to **BOTH flat & fry -114-g0bb5fb2b** (2026-06-10; lag dropped to ~3ms on both). Fix verified live on fry's reboot log: `release Vout pinning [no Vout authority]: 26.800 -> 29.000` (was sticking at the 26.8 fallback). Before the fry OTA, with flat already on -114 holding the bus high and fry stuck on -112 (pin at 26.8 fallback), fry **oscillated** 515W↔0W every ~40s (CV-squeeze) and brushed early termination; OTA stopped it. Both now carry e06c472 security fixes too. BMS-stale path left targeting fallback (correct: conservative when blind). Test in test_charger.cpp::test_release_vout_pinning_goes_to_vbat_max.
